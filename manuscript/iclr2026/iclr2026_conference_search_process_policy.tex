\section{Learning to Execute Search from Traces}
\label{sec:policy}

% Paragraph purpose: Formulate the task: an episode, one operation per step, a runtime that validates and applies each operation and ends the episode on the first invalid one, and the observation as the policy's only view of runtime-held search state.
We fine-tune a vision-language model to act as a \textbf{Search Process Policy}, which executes a declared search algorithm one step at a time instead of writing a plan. An episode fixes a task $x$ in a deterministic grounded PDDL domain, a declared algorithm $A$, an observation type $m$, and a decision budget $B$. At each step $t$, the policy reads an observation $o_t$ and emits one \textbf{Typed Search Operation}, a structured record naming an operation of $A$ and every operand that determines exploration. A \textbf{Trusted Search Runtime} checks the operation against the \textbf{Algorithm Invariant} of $A$, the ordering and bookkeeping rules that define it (Appendix~\ref{app:invariants}), and applies it. The runtime never fills in a missing operand or repairs an emission, and the first invalid step ends the episode (Appendix~\ref{app:runtime}). The frontier, visited set, and BFWS novelty tables live in the runtime's \textbf{Search Memory}, so $o_t$ is the policy's only view of the search.

% Paragraph purpose: State what a valid step contains under BFS and BFWS, separating the values the observation supplies from the bookkeeping the policy must emit.
In every algorithm, the runtime expands the head of its frontier and lists that state's grounded successors as candidates (Figure~\ref{fig:contracts}). A valid step names this state and inserts one listed successor, and a retire step closes the expansion once none is left. Under BFS, the policy picks a candidate flagged as unvisited and emits the bookkeeping of a first-in, first-out (FIFO) queue: its position at the back of the queue and whether this step removes the head. Under BFWS \citep{lipovetzky2017bestfirst}, each candidate is flagged as a duplicate or not, and each new one carries the runtime's evaluation of its novelty, its number of unachieved goals, and the frontier position this priority implies. The policy picks a non-duplicate candidate and copies that position.

% Paragraph purpose: State what a valid step contains under the two additive best-first variants, where the runtime computes every ordering value, and name the resulting setting the enumeration contract.
The two additive variants are greedy best-first search \citep{bonet2001planning}, ordered by $h_{\rm add}$, and weighted A* \citep{hart1968formal,pohl1970heuristic}, ordered by $g + 3h_{\rm add}$. Each candidate row lists $g$, $h_{\rm add}$, and the priority, all computed by the runtime, which also keeps the priority heap and its tie-break rule. The policy names the expanded state and one candidate not yet submitted, and emits no heuristic value or frontier position. In all four algorithms, each expansion thus submits every new successor, and the observation supplies the values that fix the frontier order. We call this setting the \textbf{enumeration contract}.

% Paragraph purpose: Define the three observation types, credit the external scene renderer, and state that only state facts become images while the candidate list stays textual.
The three observation types differ only in how the task's facts reach the model. The text observation lists the objects, static facts, initial and current states, and goal. The visual observation replaces these facts with images: scenes of the initial and current states drawn by the external Planimation renderer\footnote{\url{https://github.com/planimation/backend}}, and pages that render the static facts and goal. The multimodal observation gives both. In all three, the candidates, frontier summary, and recent operations stay in text, so only state facts become images.

% Paragraph purpose: Define the training target (token-level cross-entropy on Search-Trace Segments of exact-reference traces) and contrast it with a plan target in one sentence.
We train on the search trace, not the plan. Each training record, a \textbf{Search-Trace Segment}, pairs the observation at one step of a replay-verified trace of the exact reference (the declared algorithm run by the runtime) with the operation emitted there. The loss is token-level cross-entropy on that operation. A plan target would supervise only the returned action sequence, not the search steps behind it.
