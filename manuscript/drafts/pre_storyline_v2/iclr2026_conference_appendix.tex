\section{Operation Schemas}
\label{appendix}

% Paragraph purpose: Say what this appendix holds and why a reader would look here.
This appendix gives the operation vocabulary, validity checks, and rejection kinds of each declared algorithm, for readers who need the exact interface behind the Typed Search Operation definition.

% Paragraph purpose: Introduce the typed operation vocabulary and the operand ownership rule that governs all schemas.
The schemas enforce one rule: every operand that determines exploration must come from the policy (Section~\ref{sec:policy}). Each declared algorithm defines a vocabulary of operation types $\tau$, and a policy emission $u_t = (\tau_t, \theta_t)$ pairs a type from that vocabulary with an operand vector $\theta_t$ carrying every exploration-determining argument. The runtime rejects any emission whose type falls outside the declared vocabulary or whose operand vector omits a required field, so it never supplies a missing operand itself.

% Paragraph purpose: Describe the BFS operation schema at the level pinned by the sources.
\paragraph{BFS.}
The primary operation is node expansion. Its operands name the source state (the current frontier head), the grounded successors selected for insertion, the action producing each successor, and the enqueue position for each. The runtime checks that the named source matches the FIFO frontier head, that each successor results from an applicable grounded action in the source state, that the successor is unvisited, and that each insertion targets the FIFO tail. A goal-test operation names the state to test. The BFS pilot corpus exposes the facts these checks use, namely exact grounded successor candidates and full visited membership at each step.
% Evidence: BFS pilot corpus is issue #111.
% TODO: The exact BFS operation-type enumeration and per-field schema (field
% names, types, serialization format) are not recorded in any audited
% document; pin them from the codebase before release.

% Paragraph purpose: Describe the BFWS operation schema at the level pinned by the sources.
\paragraph{BFWS (complete unpruned).}
Expansion operands carry the novelty value and goal-count priority of the source state alongside the fields above. Insertion operands carry each candidate's duplicate membership, novelty, and priority. The runtime checks that the selected source has the declared best priority, that duplicate membership is correctly reported, and that insertions follow the declared ordering. The BFWS corpus exposes the facts these checks use, namely candidate duplicate, novelty, priority, insertion, and enqueue facts, at every training observation.
% Evidence: BFWS corpus is issues #57--#58.
% TODO: The exact BFWS operation-type enumeration, per-field schema, and the
% precise novelty computation (tuple arity, width parameter) are not pinned
% in audited documents; record them before release.

% Paragraph purpose: Describe the additive best-first operation schema at the level pinned by the sources.
\paragraph{Additive best-first.}
Operands carry the source state's accumulated path cost $g$, heuristic estimate $h_{\rm add}$, and composite value $f = g + w \cdot h_{\rm add}$ with $w = 3$ for the weighted variant, or $f = h_{\rm add}$ for the greedy variant. Insertion operands carry per-successor $g$, $h_{\rm add}$, and $f$. The runtime checks that the expanded state has the minimum $f$ in the frontier under the declared tie-breaking rule and that all arithmetic is consistent.
% TODO(schema): Per-field additive operation serialization remains to be pinned; the tie-break is pinned below from the executed controller.

% Paragraph purpose: State the validity preconditions as an ordered rejection hierarchy.
\paragraph{Validity preconditions.}
Every emission passes through the same ordered sequence of checks, and the first check it fails rejects it with that kind and ends the episode. Each recorded rejection kind therefore names the earliest check an emission failed. The checks run in the following order.

\begin{enumerate}[leftmargin=*, itemsep=1pt, parsep=1pt]
\item \textbf{Parse.} The raw output must parse into a well-formed Typed Search Operation with a recognized type and complete operand vector. A failure is recorded as \texttt{malformed\_output}.
\item \textbf{Source identity.} The named source state must match the state the algorithm expects. A failure is recorded as \texttt{source\_state\_mismatch}.
\item \textbf{Action applicability.} Every grounded action in the operands must be applicable in the source state. A failure is recorded as \texttt{inapplicable\_grounded\_action}.
\item \textbf{Successor schema.} Any named successor state must satisfy the domain schema. A failure is recorded as \texttt{schema}.
\item \textbf{Successor effects.} The named successor must match the declared effects of the applied action. A failure is recorded as \texttt{effect}.
\item \textbf{Static context.} Referenced predicates, objects, and constants must be consistent with the task instance. A failure is recorded as \texttt{static\_context}.
\item \textbf{Frontier discipline.} The frontier manipulation must respect the declared ordering (FIFO for BFS, priority for BFWS, $f$-order for additive best-first). A failure is recorded as \texttt{invalid\_frontier\_operation}.
\item \textbf{Algorithm invariant.} Any remaining algorithm-specific constraint not covered above. A failure is recorded as \texttt{other\_invariant\_violation}.
\end{enumerate}

% Paragraph purpose: Separate format failures from search failures, and give the random-valid control's single failure kind.
Rejections fall into two categories, format failures and search failures. \emph{Malformed-output} rejections never reach the operation checker, whereas \emph{post-parse rejections} parse but fail a runtime check. The oracle-assisted random-valid control emits only runtime-accepted operations, so its single failure kind is \texttt{expansion\_budget\_exhausted}, recorded when the frozen episode budget runs out before a goal is reached.

% Paragraph purpose: State what the rejection taxonomy shows and point to its table.
\paragraph{Rejection counts.}
The base model fails mostly on format, while learned policies fail mostly after parsing, on algorithm invariants (Table~\ref{tab:appendix-rejection}). The counts come from the failure-mechanism calibration, which classified all 905 failures across 2,910 replay-verified episodes with zero unclassified. The \texttt{effect}, \texttt{schema}, and \texttt{static\_context} kinds arise in successor-prediction episodes, where the model generates a dynamic-state successor.

\section{Algorithm Invariant Definitions}
\label{app:invariants}

% Paragraph purpose: Say what this appendix holds and why a reader would look here.
This appendix states the invariant the runtime enforces for each declared algorithm, which Section~\ref{sec:policy} defines only in outline.

% Paragraph purpose: State that invariants are per-operation checks and therefore say nothing about episode outcomes.
The Trusted Search Runtime checks the following invariants on every operation. Because each invariant constrains a single step, stepwise validity and invariant compliance do not establish termination, completeness, optimality, or episode success (Section~\ref{sec:policy}).

% Paragraph purpose: BFS invariant.
\paragraph{BFS.}
BFS keeps its frontier as a FIFO queue, so every expansion must select the queue head as its source and every insertion must target the queue tail. A state already in the visited set must not be re-inserted. This invariant is sufficient for completeness in finite state spaces with unit-cost transitions.

% Paragraph purpose: BFWS invariant.
\paragraph{BFWS (complete unpruned).}
The frontier is a priority queue ordered first by novelty rank (lower is better), then by goal count among states with equal novelty. No generated successor is pruned. A successor whose state already appears in the frontier or visited set is not re-inserted.
% TODO: The exact novelty definition (tuple arity, width parameter, and
% tie-breaking within equal novelty and equal goal count) is not pinned in
% any audited document. Record the precise rule before release.

% Paragraph purpose: Weighted additive best-first invariant.
\paragraph{Additive best-first, weighted ($w = 3$).}
The frontier is a priority queue ordered by $f(s) = g(s) + 3 \cdot h_{\rm add}(s)$, where $g(s)$ is accumulated path cost and $h_{\rm add}(s)$ is the additive heuristic. Among equal-$f$ states the lower generation serial is expanded first. The expanded state is the heap head. A successor with lower $g$ than an existing frontier entry for the same state reopens that entry with improved cost.
% Evidence (executed controller): examples/planning_benchmark_slice/best_first_controller.py BestFirstController.start_expansion and apply_operation, with PDDLStateAuthority.applicable_actions in pddl_state.py sorting by GroundedAction.serialize.

% Paragraph purpose: Greedy additive best-first invariant.
\paragraph{Additive best-first, greedy.}
The frontier is ordered by $h_{\rm add}(s)$ alone, with no path-cost component, then by ascending generation serial among ties. The expanded state is the heap head. Reopen and duplicate rules follow the weighted variant.
% Paragraph purpose: Show that the executed controller's serial assignment produces the enumeration-contract identity, and that the identity is specific to this runtime.
The executed controller's serial assignment is what makes the enumeration contract insensitive to submission order. In both additive settings, \texttt{BestFirstController.start\_expansion} assigns serials before submissions, in the deterministic \texttt{PDDLStateAuthority.applicable\_actions} order (sorted by \texttt{GroundedAction.serialize}). The \texttt{BestFirstController.apply\_operation} heap orders entries by (priority, serial, state identifier, path cost), and \texttt{finish\_expansion} requires the full candidate set. Submission permutations therefore leave frontier order unchanged on the enumeration contract. A runtime assigning serials in submission order would not be submission-order invariant and would not show this identity, so the identity is a property of this runtime (Appendix~\ref{app:results-counterfactual}).
% Evidence: examples/planning_benchmark_slice/{pddl_state.py PDDLStateAuthority.applicable_actions,best_first_controller.py BestFirstController.start_expansion/apply_operation/finish_expansion}; outputs/native-arms/v1/identity-audit.json structural_basis.


\section{Trusted Search Runtime}
\label{app:runtime}

% Paragraph purpose: Say what this appendix holds and why a reader would look here.
This appendix gives the runtime's guarantees and its step and episode pseudocode, for readers checking that the runtime never chooses or repairs on the policy's behalf.

% Paragraph purpose: State the three guarantees of the runtime.
The runtime provides three guarantees that hold across all declared algorithms.

\begin{enumerate}[leftmargin=*, itemsep=1pt, parsep=1pt]
\item \textbf{No-repair property.} The runtime validates, applies, persists to Search Memory, or rejects each emission. It never chooses omitted operands, reorders candidates, silently repairs an invalid emission, or substitutes a default search decision.
\item \textbf{Reject-and-terminate.} On the first rejected emission the episode terminates with the rejection kind recorded. There is no retry path.
\item \textbf{Replay determinism.} Replaying the raw emissions $u_{1:T}$ against the same task instance and the same initial Search Memory reproduces the explored trace. Any step whose outcome depends on runtime repair would violate this property.
\end{enumerate}

% Paragraph purpose: Say how the pseudocode maps to the ordered checks and the budgeted episode loop.
The two procedures below make the guarantees concrete. \textsc{Step} applies the checks of Appendix~\ref{appendix} in their fixed order, and \textsc{Episode} wraps it in a budgeted loop that ends at the first rejection or at the goal.

\begin{quote}
\small
\begin{tabbing}
\hspace{1.5em}\=\hspace{1.5em}\=\hspace{1.5em}\=\kill
\textbf{procedure} \textsc{Step}($u_t$, $M_{t-1}$, $A$, $x$) \\
\> \textit{// Phase 1: Parse the raw emission} \\
\> \textbf{if} $u_t$ does not parse as $(\tau, \theta)$ with $\tau \in \mathrm{vocab}(A)$ \textbf{then} \\
\>\> \textbf{return} \textsc{Reject}(\texttt{malformed\_output}) \\[2pt]
\> \textit{// Phase 2: Validate source identity} \\
\> \textbf{if} $\theta.\mathrm{source} \neq \mathrm{expected}(A, M_{t-1})$ \textbf{then} \\
\>\> \textbf{return} \textsc{Reject}(\texttt{source\_state\_mismatch}) \\[2pt]
\> \textit{// Phase 3: Validate operands against the task and state} \\
\> \textbf{for each} grounded action $a$ named in $\theta$ \textbf{do} \\
\>\> \textbf{if} $a$ is not applicable in $\theta.\mathrm{source}$ under $x.D$ \textbf{then} \\
\>\>\> \textbf{return} \textsc{Reject}(\texttt{inapplicable\_grounded\_action}) \\
\> \textbf{for each} successor state $s'$ named in $\theta$ \textbf{do} \\
\>\> \textbf{if} $s'$ violates the domain schema \textbf{then} \\
\>\>\> \textbf{return} \textsc{Reject}(\texttt{schema}) \\
\>\> \textbf{if} $s' \neq \mathrm{effects}(a, \theta.\mathrm{source})$ \textbf{then} \\
\>\>\> \textbf{return} \textsc{Reject}(\texttt{effect}) \\
\> \textbf{if} any static-context reference in $\theta$ is inconsistent with $x$ \textbf{then} \\
\>\> \textbf{return} \textsc{Reject}(\texttt{static\_context}) \\[2pt]
\> \textit{// Phase 4: Check Algorithm Invariant} \\
\> \textbf{if} frontier discipline of $A$ is violated by $(\tau, \theta, M_{t-1})$ \textbf{then} \\
\>\> \textbf{return} \textsc{Reject}(\texttt{invalid\_frontier\_operation}) \\
\> \textbf{if} any other invariant of $A$ is violated \textbf{then} \\
\>\> \textbf{return} \textsc{Reject}(\texttt{other\_invariant\_violation}) \\[2pt]
\> \textit{// Phase 5: Apply and persist} \\
\> $M_t \leftarrow \mathrm{apply}(\tau, \theta, M_{t-1})$ \\
\> \textbf{return} \textsc{Accept}($M_t$)
\end{tabbing}
\end{quote}

\begin{quote}
\small
\begin{tabbing}
\hspace{1.5em}\=\hspace{1.5em}\=\hspace{1.5em}\=\kill
\textbf{procedure} \textsc{Episode}($x$, $A$, $\phi_m$, $B$) \\
\> $M_0 \leftarrow \mathrm{InitSearchMemory}(A, x)$ \\
\> \textbf{for} $t = 1, 2, \ldots, B$ \textbf{do} \\
\>\> $o_t \leftarrow \phi_m\bigl(c_t(x, M_{t-1})\bigr)$ \hspace{2em} \textit{// build observation} \\
\>\> $u_t \leftarrow \pi(o_t)$ \hspace{6.4em} \textit{// policy emission} \\
\>\> $r \leftarrow$ \textsc{Step}($u_t$, $M_{t-1}$, $A$, $x$) \\
\>\> \textbf{if} $r$ is \textsc{Reject}(\textit{kind}) \textbf{then} \\
\>\>\> \textbf{return} $(t, \textsc{Fail}, \textit{kind})$ \\
\>\> $M_t \leftarrow r.M$ \\
\>\> \textbf{if} $\mathrm{GoalTest}(M_t, x.G) = \textsc{True}$ \textbf{then} \\
\>\>\> \textbf{return} $(t, \textsc{Success})$ \\
\> \textbf{return} $(B, \textsc{Fail}, \texttt{expansion\_budget\_exhausted})$
\end{tabbing}
\end{quote}

% Paragraph purpose: Note budget enforcement: rejected emissions are charged.
Each call to \textsc{Step} consumes one unit of the frozen episode budget $B$ whether the emission is accepted or rejected, so invalid operations are charged to the budget (Section~\ref{sec:design}).

\section{Statistics}
\label{app:statistics}

% Paragraph purpose: Say what this appendix holds and why a reader would look here.
This appendix states the interval, test, margin, and tiny-strata conventions behind every reported contrast, for readers judging what an interval licenses.

% Paragraph purpose: State that main-program intervals are descriptive bounds, and the default contrast procedure behind them.
\paragraph{Default contrast procedure.}
Main-program intervals are descriptive bounds, not evidence of broad superiority, because they come from one training seed and panels of 24 or fewer instances. Contrasts are paired by whole task instance, and paired differences use a bootstrap with 10,000 resamples at seed 1729 and 95\% percentile intervals.

% Paragraph purpose: Pin the BFWS gate bound to its two-sided percentile interval.
The BFWS gate's reported lower bound is the 0.025 quantile, i.e., the lower endpoint of a two-sided 95\% percentile interval. The gate follows the default procedure, with confidence level 0.95 and 10,000 paired whole-instance resamples (bootstrap seed 1729).
% Evidence: BFWS gate is issue #59. configs/experiments/bfws_phase_threshold_v1.json bootstrap {confidence_level 0.95, resamples 10000, seed 1729,
% interval paired_percentile_bootstrap}; docs/issue-59-bfws-structural-gate.md L250-253 (lower bound 0.2).

% Paragraph purpose: State the tiny-strata rule: no intervals below 8 episodes, and no silent pooling or dropping.
\paragraph{Tiny-strata rule.}
No intervals are computed over strata with fewer than 8 episodes, so such strata are reported as descriptive only. They are listed explicitly and never silently pooled or dropped.

% Paragraph purpose: State that no transfer comparison survives correction, then the test procedure.
\paragraph{Transfer tests.}
No transfer comparison survives multiple-testing correction, and this non-significance is not evidence of equivalence. Transfer comparisons use McNemar exact tests against the per-example base predictions, with Holm correction across all 36 adapter-by-benchmark comparisons, and the minimum adjusted $p$ in the executed transfer branch is 0.8156.
% Evidence: outputs/expanded-study/v1/transfer-paired-analysis.json min_holm_p 0.81561 over 36 comparisons.
% Evidence: 36 Holm-corrected McNemar comparisons per synthesis-v1/transfer-paired.csv (Table tab:results-transfer).

% Paragraph purpose: State the follow-up bootstrap seeds separately from the main-program default.
\paragraph{Follow-up bootstrap conventions.}
The follow-up windows fix their own bootstrap seeds, separate from the main program's seed 1729 default. The native-arms contrasts and the choice-frontier contrasts use a paired whole-problem bootstrap at seed 61813 with 10,000 resamples and 95\% percentile intervals, and the second-backbone v3 contrasts (stress test R3) use seed 1729 with 10,000 resamples. The comparator-zoo metrics use a task-cluster bootstrap that draws nine tasks with replacement at seed 133 for 10,000 draws, keeping both additive cells and all random seeds inside their task cluster.

% Paragraph purpose: State the materiality rule and the non-equivalence sentence requirement.
\paragraph{Materiality and non-equivalence.}
A follow-up contrast is material when its 95\% interval excludes zero, and equivalence can be read only against a pre-registered margin. The follow-up protocols through the comparator zoo pre-registered no equivalence margin, so a non-material contrast there supports neither superiority nor equivalence. The later choice-frontier protocols pre-register an equivalence margin of $\pm 0.05$ for $D$ (adapter minus random-valid M1) and for the DAgger change $\Delta$, and none for the separation $S$ from an exact-$\epsilon$ rung, so a non-separated $S$ is not equivalence to the rung. Wherever the text reports a non-material contrast or a comparison that fails Holm correction, an adjacent sentence states that non-significance is not equivalence.
The exact sign-flip $p$ value is likewise descriptive. It enumerates all $2^n$ sign vectors of the $n$ per-task differences, is two-sided, and tests a zero difference, so it never supports equivalence.

\section{Modality Adapters and Observation Contract}

% Paragraph purpose: Say what this appendix holds and why a reader would look here.
This appendix defines the observation adapters and what each one exposes to the policy, which bounds any reading of the modality results.

% Paragraph purpose: State the decision-sufficiency requirement every adapter meets, then define the adapter map.
Every adapter must be decision-sufficient: its observation must expose every fact the exact reference uses to resolve the current step under the declared algorithm. Three fixed Modality Observation adapters are declared. Each maps a decision context $c_t$ (the canonical task context plus the decision-relevant view of Search Memory $M_t$) to an observation $o_t = \phi_m(c_t)$ presented to the policy, and the adapter stays fixed for an entire training or evaluation cell.

% Paragraph purpose: text-state adapter.
\paragraph{text-state.}
The state, goal, and search context are serialized as a compact relational representation. Object identities, predicate names, and all Search Memory contents (frontier, visited set, algorithm-specific state) appear as structured text.

% Paragraph purpose: visual-state adapter.
\paragraph{visual-state.}
The state and goal are rendered as a pair of 128$\times$128 pixel images, a rendered state image and a partial-goal constraint image. Object labels are not embedded in the rendered image. Search Memory contents and the grounded candidate list remain in the textual serialization, even in this adapter. This is the published frozen \texttt{visual-state} arm that the native arms below are compared against.

% Paragraph purpose: State that the figures show the policy's own scenes without retouching, and how each figure's images were checked.
The figures show the scenes the policy saw, enlarged but never retouched. Figure~\ref{fig:teaser} displays unchanged cached 128-pixel policy scenes enlarged by nearest-neighbour sampling. The validation filmstrips in Appendix~\ref{app:qualitative} show label-free 256-pixel re-renders, used only after the same scenes at the policy's 128-pixel resolution matched the cached inputs pixel for pixel. The held-out puzzle shows the original cached 128-pixel frames instead, because re-rendering its initial state changes tile glyphs. Figure scripts retain the exact image paths and checks.

% Paragraph purpose: multimodal-state adapter.
\paragraph{multimodal-state.}
The observation combines the text-state serialization and the visual-state rendered images. The policy receives the relational text and the image pair jointly.

% Paragraph purpose: Record the executed native-arms v2 adapters and how they reduce the textual payload.
\paragraph{Native image-only arms.}
Two further adapters executed under the native-arms v2 contract. \texttt{visual-nomem-state} keeps only the static task interface and the grounded, unscored candidate menu as text, and carries state facts in the current rendered scene alone. \texttt{visual-seq-state} adds up to $K{=}8$ rendered history frames, each labelled with its absolute path depth. Neither receives textual Search Memory, accepted deltas, $g$/$h$/priority scalars, candidate scores, or membership flags.

% configs/experiments/native-arms/native-arms-v2-protocol.json history_window.

% Paragraph purpose: State the text-scaffold caveat: search bookkeeping always travels as text, and the corruption suite agrees.
\paragraph{Text-scaffold caveat.}
In all three declared adapters, including visual-state, search bookkeeping travels as text. Rendered images carry the planning state and goal visuals, but the frontier, visited set, novelty counters, and candidate list are always serialized as structured text. The observation-corruption suite is consistent with this (Table~\ref{tab:results-corruption}). Copyability-preserving text shuffling drops success by up to $-0.944$ (text) and $-0.722$ (multimodal), while visual corruption costs at most $-0.111$ with intervals that include zero.

\section{Retained-Infrastructure Feasibility Notes}

% Paragraph purpose: Scope the section: feasibility evidence, not efficacy.
This appendix defines the verified infrastructure components behind corpus generation, evaluation, and evidence production. They are feasibility evidence for the runtime and rendering pipeline and cannot support a Search Process Policy efficacy claim.

% Paragraph purpose: Define the plan pipeline terms.
\paragraph{Plan pipeline.}
\textbf{Plan Submission} transmits a supplied plan from the project adapter to a planning or rendering backend. \textbf{Plan Interpretation} converts the submitted plan into the backend's ordered action representation. An \textbf{Action Sequence} is the canonical identity of a supplied plan as a normalized, ordered sequence of grounded action predicates. Casing and whitespace are not part of its identity.

% Paragraph purpose: Define the rendering pipeline terms.
\paragraph{Rendering pipeline.}
\textbf{Render Production} creates a visualisation output and its rendered image for a planning state. \textbf{Render Validation} confirms that the produced visualisation and image satisfy declared structural and semantic checks. \textbf{Plan Provenance} links a produced visualisation to the exact supplied plan that the backend interpreted.

% Paragraph purpose: Define the certification and evidence terms.
\paragraph{Certification and evidence.}
\textbf{Integration Certification} is the finding that Plan Submission, Plan Interpretation, Plan Provenance, Render Production, Render Validation, and required execution-isolation checks all passed. An \textbf{Attempt} is one authorized, immutable execution with its own identity and retained outcome, whether successful or not. An \textbf{Evidence Bundle} is the self-contained records from an Attempt that allow an independent reproducer to verify its claims offline. The retained infrastructure supplies deterministic compact delta/event evidence with semantic replay while preserving search semantics, serving the replay-determinism requirement of the Trusted Search Runtime.
% Evidence: compact delta/event evidence per issue #110.

% Paragraph purpose: Note historical CGAS terms and their claim boundary.
\paragraph{Historical terms.}

\section{Choice-Frontier Contract and Comparator Selectors}
\label{app:cf-contract}

% Paragraph purpose: Say what this appendix holds and why a reader would look here.
This appendix specifies the choice-frontier contract, its corpus derivation, its metrics, and the comparator selectors, for readers reproducing the measurement that Section~\ref{sec:results-ladder} validates.

% Paragraph purpose: The menu withholds scores, positions, and search bookkeeping, so a choice can rest only on the scenes and task pages.
\paragraph{Menu and observation.}
The choice-frontier observation withholds every score, position cue, and search counter, so a choice can rest only on the rendered scenes and the task pages. At each decision the runtime exposes the live frontier as an unscored menu of opaque labels $c_0, \ldots, c_K$. The labels are assigned after a seeded Fisher--Yates permutation of the generation-serial member order, with a per-decision seed derived from master seed 51131 and a hash of the member state identifiers, so a label carries no positional information. The observation holds static task-context pages, the unlabelled 128px initial-state scene, one unlabelled 128px scene per frontier state in menu order, and the partial-goal pages. Its text payload is limited to the algorithm name, the label list, the representation tag, the schema version, and the frozen legend, and a leak check fails closed on any forbidden key marker.
% Evidence: docs/experiments/choice-frontier/issue-132-design.md section 2 (menu, seed rule, payload, assert_no_text_leak).

% Paragraph purpose: The output contract admits one offered label per decision, and the first invalid emission ends the episode.
\paragraph{Output and validation.}
The output contract admits exactly one offered label per decision, and the first invalid emission ends the episode. The policy emits canonical JSON with the single key \texttt{expand\_choice} and a label value. The runtime rejects malformed JSON, a wrong key set, a non-string label, a label not offered by the pending menu, and a label bound to a non-live member, and it records the rejection as \texttt{deterministic\_invalid\_operation}. An episode otherwise ends as \texttt{goal\_reached}, \texttt{frontier\_exhausted}, \texttt{decision\_budget\_exhausted}, or \texttt{expansion\_budget\_exhausted}.
% Evidence: issue-132-design.md section 2 (output contract, rejections, termination reasons).

% Paragraph purpose: The runtime performs every expansion, so one decision is one choice, and the goal-at-selection rule fixes the exact reference's decision count.
\paragraph{Expansion and budget.}
The policy only chooses and the runtime does everything else, so one submitted choice is one decision. On acceptance the runtime removes the chosen member from the frontier and expands it atomically. Candidate generation, serial assignment, admission, duplicate detection, reopening, and expansion bookkeeping are inherited unchanged from the frozen additive best-first controller, which is not modified, and per-candidate admissions stay runtime-internal. Selecting a member that satisfies the goal solves the task without an expansion and without budget charge. The exact episode therefore takes its reference expansion count plus one decisions. Decision and expansion caps both equal 2$\times$ the reference expansion count.
% Evidence: issue-132-design.md section 2 (expand_member, inherited BestFirstController internals, goal at selection,
% decision_cap = expansion_cap = 2 x reference_expansions); issue-132-closeout.md Erratum items 1 and 5.

% Paragraph purpose: Each training record teaches the exact reference's own choice, derived by replaying the frozen exact traces through the new contract.
\paragraph{Corpus derivation.}
Each training record teaches the exact reference's own choice, the label bound to the heap head. The training corpus was derived on CPU by replaying the frozen exact traces through the new contract and verified expansion-for-expansion against them (58 episodes bit-exact). Records are selected through the frozen matched-modalities membership, which indexes enumeration-contract decisions, and each such decision maps to the expansion whose candidate set it submitted into. Unique (task, expansion) pairs in first-occurrence order form the base set, and a round-robin over the frozen task order tops the set up to 512 training records per algorithm. Diagnostics are the unique expansions of the frozen diagnostic identifiers, with no top-up.

% Paragraph purpose: Training ran only after five fail-closed gates passed, and the pinned preparation report records the corpus counts.
Training ran only after five fail-closed gates passed. The gates check expansion-for-expansion agreement with the stored exact traces, a token budget of measured input plus 384 within 32,768, the text-leak check, image resolution, and identity with the frozen membership. The pinned preparation report records outcome PASS over 29 tasks, 1,046 records (512 training and 11 diagnostic per algorithm), 3,544 scenes, and 58 episodes re-derived bit-exact. The smoke gate accepted 40/40 model calls.

\paragraph{Training and replay.}
Both adapters trained to completion under the frozen recipe, and their episodes are independently replayed. Each of the two cells trains a LoRA adapter (rank 64, $\alpha$ 128) for 16 updates on its 512 records at seed 17 with the frozen expanded-program recipe. Both jobs completed all 16 steps and saved final adapters, and only the later post-save summary construction failed. Their reports were therefore recovered from the primary training-state artifacts with provenance marked, no retraining was needed, and the training audit passes on the recovered reports. At finalize, independent replay re-derives every menu binding, payload, and trusted transition from the stored events and checks pixel bindings against the retained scenes.

% Paragraph purpose: The comparator selectors replace only the choice, so every other search step stays additive, and their replay omits image bindings.
\paragraph{Comparator selectors.}
The comparator selectors replace only the choice. Each selector's choice is mapped back to the menu binding, and every candidate still enters through the additive admission path, so frontier admission, duplicate detection, $h_{\rm add}$ computation, reopening, and serial ordering stay additive for \texttt{bfs-order} and novelty-first selection alike. Novelty-first selection uses positive PDDL state atoms as its novelty features, and its seen-feature sets advance only when a state is expanded, including the initial expansion. Each new episode is re-run against an independently constructed PDDL authority, which checks menus, decisions, admissions, and result dictionaries. This replay covers the model input, menu, actions, admissions, and budget, but selector episodes neither generate nor replay image bindings. The optimal costs $C^*$ come from one offline shortest-plan computation per task with replay-verified plans, and the native four-algorithm reference costs are recorded separately from the zoo.
% Evidence: docs/experiments/choice-frontier/issue-133-protocol.md (label mapping, additive admission path, novelty features,
% independent PDDL authority, one offline C* computation per task); #133 closing comment (no image-binding replay, native references
% checked separately); outputs/choice-frontier/o4/metrics/{optimal-costs,native-four-algorithm-reference-costs}.json.

% Paragraph purpose: The protocol fixes each metric's edge cases so every arm is scored by one rule, and the goal-at-selection rule fixes the exact reference's M1 at 0.875.
\paragraph{Metric computation.}
The protocol fixes each metric's edge cases so that every arm is scored by the same rule. Under M1 an episode solves at multiplier $m$ when its first goal selection occurs within $\lfloor m R_t \rfloor$ decisions with at most $\lfloor m R_t \rfloor$ preceding expansions, where $R_t$ is the additive exact-reference expansion count. Unsolved 2$\times$ runs count as failures at every $m$, the same prefix truncation applies to every arm, and task and algorithm weights are equal. M2 also has a censored form, in which failures are right-censored at the budget rather than assigned a fictitious expansion count. M3 counts transitions along the selected goal state's trusted predecessor chain and is undefined, never imputed, for unsolved episodes. M4 measures agreement with the current additive heap head over decisions with at least two live choices, against a chance rate equal to the decision-weighted mean of $1/K$. M5 restricts to tasks where the mean 2$\times$ random-valid solve indicator lies strictly between 0 and 1.
The goal-at-selection rule fixes the reference's own M1. Goal selection is the $(R_t{+}1)$-th decision, so the exact reference fails at $m = 1$ and scores M1 $= 0.875$ by construction. An arm that reaches the goal in fewer decisions can therefore exceed the reference, as the privileged hadd-greedy selector does on the validation, held-out, and unscreened panels (0.882, 0.928, and 0.906).

% Paragraph purpose: Show that LLM-First Search keeps every unexpanded alternative, which makes a zero-token random chooser a complete search; define random-valid and the decision unit.
LLM-First Search keeps every unexpanded alternative, and this makes a zero-token random chooser a complete search. It is a type-C interface. The model scores candidates, and the search expands the argmax child or pops the highest-valued frontier node, so every unexpanded alternative stays in the frontier. Random-valid answers every query with independent uniform draws, spends zero tokens, and makes no model call. It uses the five seeds of the first audit, and a decision is one node expansion after the root.
